Reference document — not a checklist itself

How to build a Land Use Bylaw review checklist

This is the build spec behind IG_Zoning_Review_Checklist.html, generalized so any Calgary land use district (R-CG, C-COR3, M-CG, S-SPR, etc.) can be turned into the same kind of standalone, self-contained review tool. Follow this document top to bottom when building the next one — it defines the data shape, the UI contract, the persistence model, and the QA bar every checklist in this family has to clear.

00Purpose & scope

Each checklist is a single, dependency-free .html file a reviewer opens locally (double-click, no server, no install) to work through every applicable Land Use Bylaw (LUB) requirement for one district on one project, track a Pass / Fail / Pending Info / N/A status against each one, and export a record of the review as CSV.

The tool is a generic template for the district, not a substitute for reading the bylaw. It should always say so explicitly (see the Instructions tab pattern in §04), and it should always point back to the current consolidated bylaw on calgary.ca for anything outside its scope: Part 1/2 definitions, subdivision requirements, Direct Control variations, registered Comprehensive Sign Programs, restrictive covenants, and Airport Vicinity Protection Area maps.

01Architecture overview

Every checklist in this family is organized into the same four review buckets, because every Calgary land use district's rules break down the same way regardless of category. Only the content inside each bucket — and which Part/Division numbers it maps to — changes district to district.

Tab (canonical key)What lives hereAlways applicable?
General rules
key: general		The rules that apply to every district in the same broad land use category as the one you're building (Residential, Commercial, Industrial, Special Purpose, etc.) — landscaping, screening, setback projections, fences, signage siting, etc.Yes, no exceptions
District rules
key: district		The specific district's own division: purpose statement, permitted/discretionary use lists, building size, FAR, height, setbacks, screening.Yes, no exceptions
Citywide rules
key: citywide		Rules Governing All Districts (Part 3 in the current bylaw) — public realm setbacks, airport vicinity, floodway, lighting, signs, parking/loading, servicing.Yes, identical across every district in the city, regardless of category
Use rules
key: use		Every permitted/discretionary use listed under the district, mapped to its use-definition section. Gated behind a use-selector — see §05.Only for uses actually proposed
Why this shape: it mirrors how a reviewer actually works a Calgary DP file, in any category — confirm the use is allowed, confirm the district's own numeric standards, confirm the citywide overlay rules, then confirm anything use-specific. Keeping that order in the UI keeps the tool aligned with how the reviewer already thinks, independent of which category the district falls under.

02Sourcing content from the bylaw

Before writing any code, build a small "district worksheet" mapping the four tabs to the bylaw's actual part/division numbers for that district. Land Use Bylaw 1P2007 groups districts by category, and each category's general + district rules live under a different part — confirm current numbers against the live consolidated bylaw before starting, since they do shift. As a starting reference:

Per-item extraction rule

For each bylaw section that becomes a checklist item, write a plain-English summary a reviewer can act on without opening the bylaw first — the actual pass/fail criteria, not just "see Section X." Keep the section number in its own field so it's always traceable back to source. Where the bylaw is ambiguous, reuses a number for two different rules, or was later deleted/superseded, say so directly in the summary rather than silently dropping the item.

Don't paraphrase away specificity. Numbers, thresholds, and cross-references are the whole point of a review checklist — "min. 2.0 m fence" beats "adequate fencing required" every time.

03Data model & ID conventions

All checklist content lives in one JS object, CHECKLIST_DATA, keyed by the four canonical tab keys from §01 — general, district, citywide, use. Using these fixed keys (rather than naming them after a specific Part number) is what lets every checklist in the family share the same rendering, session, and CSV logic unchanged, regardless of which category's Part numbers actually apply. Every item is a flat object with exactly four fields:

const CHECKLIST_DATA = {
  "general": [
    { "id": "gen-0", "sec": "897", "title": "Projections Into Setback Areas",
      "summary": "Buildings generally can't sit in a setback. Eaves may project max 0.6 m..." },
    // ...one object per checklist item
  ],
  "district": [ /* district-specific rules */ ],
  "citywide": [ /* rules governing all districts */ ],
  "use": [
    { "id": "use-2", "sec": "149", "title": "Auto Body and Paint Shop",
      "summary": "Permitted — 907(2)" } // summary MUST start "Permitted" or "Discretionary"
  ]
};
FieldRule
idStable, unique, never reused — this is what the CSV round-trip (§06) matches on. Convention below.
secThe bylaw section number as a string (so "915 (Front Setback)" or "—" for undefined references are both valid).
titleShort article name / use name, sentence case.
summaryThe plain-English rule text. For use tab items specifically, this field must begin with the literal word Permitted or Discretionary — the use-selector dropdown (§05) filters on that prefix, and nothing else is allowed to appear in it.

ID prefix convention

Tab keyID prefixExample
generalgen-Ngen-0, gen-1...
districtdis-Ndis-0, dis-1...
citywidecw-Ncw-0, cw-1...
useuse-Nuse-0, use-1...

These four keys and prefixes stay identical across every district and every category — Residential, Commercial, Industrial, Special Purpose, all use the same general/district/citywide/use structure. The actual Part/Division numbers for that category (from your §02 worksheet) live in the TABS array's label/short-code metadata, not in the key names, so nothing about the data model itself needs to change between categories. Whatever prefix scheme you use, keep it consistent within that file and never renumber an existing id once a checklist has shipped — it breaks CSV re-import for anyone with an in-progress export.

04UI component spec

Reuse this component set as-is; only the tab labels/short codes and the sidebar project fields are district-specific.

Sidebar

  • Project fields: Project number, Project name, Site address / legal desc., DP / file no., Reviewer. Project number drives the export filename (§06) — always include it, always first.
  • Tab nav: Instructions + the 4 review tabs, each showing a live done/total count.
  • Overall progress: a single ruler/percentage bar summing done/total across all 4 tabs.
  • Session controls: Export session (.csv) / Import session (.csv), plus a visible warning that nothing autosaves (see §06 — this is not optional).

Instructions tab

Every checklist opens on an Instructions tab covering: the intended workflow order (general → district → citywide → use), what the tool explicitly does not cover, the status legend, and the no-autosave warning restated in context.

Review card (one per checklist item)

  • Section badge + title
  • Plain-English summary
  • Four status pills: Pass / Fail / Pending Info / N/A — click to set, click again to clear
  • Collapsible notes field (free text — drawing refs, follow-ups, evidence)

Panel tools

Search box (matches section/title/summary) + "Fails only" / "Pending only" filter chips, on every tab. The use tab additionally gets the use-selector (§05).

Stat strip

Per-tab counts by status (Pass / Fail / Pending Info / N/A / Not started), computed off the in-scope item set for that tab — see §05 for why the use tab is scoped differently from the other three.

05The use-selector pattern (use tab)

The use tab is structurally different from the other three: a district might permit 60+ uses, but only 1–3 are ever actually proposed on a given project. Don't list all of them as cards by default — gate them behind a dropdown.

  1. Filter to selectable uses only. A use-tab item is offered in the dropdown only if its summary starts with Permitted or Discretionary (regex: /^(Permitted|Discretionary)\b/i). Nothing else is ever shown — no deleted/reserved entries, no non-use sections.
  2. Group by status. Two <optgroup>s — "Permitted uses" and "Discretionary uses" — each sorted alphabetically by title so a 60-item list stays scannable.
  3. Selecting adds, it doesn't replace. Picking an option sets that item's proposed flag true, the dropdown resets to the placeholder, and a card for that use appears below with the normal status pills/notes to test against it. Repeat to add more uses.
  4. Removing is explicit. Each card gets a "Remove from review" action that clears proposed and drops the card — no destructive click-to-toggle checkbox.
  5. Scope progress to selections. The use tab count, stat strip, and overall progress bar should only count uses that have been added — an untouched 64-use district shows 0/0 for that tab until the reviewer actually picks something, not 0/64.
Still export everything. Scoping the UI to selected uses doesn't change what gets exported — the CSV always includes every use in the district with its Proposed Yes/No flag (§06), so the record stays a complete statement of what was and wasn't reviewed.

06Session model — CSV is the only persistence

This is a standalone file with no server and no guaranteed browser storage. Do not call any browser storage API (no window.storage, no localStorage) — state lives in memory for the tab only, and the CSV export/import pair is the entire persistence mechanism.

Filename convention

[Project Number] - [YYYY-MM-DD] - LUB Review.csv

Sanitize the project number for filesystem-unsafe characters (\ / : * ? " < > |) before building the filename.

07Conditional building-status checkboxes

Some districts flip a use's status — or its very availability — based on a binary fact about the building itself, not about the use. The pattern first appeared in Industrial – Business (I-B): §923(2)/§924(1) makes a block of uses Permitted if they're in an existing approved building but Discretionary if the building is proposed or a proposed addition; separately, §924(3) makes a different block of uses Discretionary only if the building already contains one of the §923(2)-list uses — otherwise they aren't available at all. Neither condition is a use-specific fact, so it doesn't belong on any one card; it belongs to the project.

Scope — building-status facts only. This pattern is for binary yes/no facts about the building (new vs. existing; already contains a listed use). Don't extend it to other conditional flips — e.g. I-G's water/sewer servicing flip (§908(1)) stays handled the old way: a plain-English rule item in the district tab, no live-computed logic — unless a future task explicitly asks for that to change.

Where they live

Two checkboxes in the sidebar, directly below the existing project fields, visually grouped under a small "District conditions" label so they read as project facts rather than review data — never per-use, never inside a card.

State & persistence

Add both as booleans on state.project alongside the five existing project fields (e.g. newBuilding, buildingHasListedUse), and add both to META_FIELDS (§06) so they export and re-import exactly like every other project fact — a reloaded session must show the same computed statuses it had when exported.

Behavior

  • Every affected use-tab item's displayed status label — and which optgroup it sorts into, or whether it's offered at all — is computed live from these booleans at render time, never hardcoded into CHECKLIST_DATA.
  • Toggling a checkbox is a state-changing action: wire it through the same shared refreshEverything() call (§08) as a status pill click, so the use-selector dropdown, any open cards' labels, and the stat strip all update together.
  • If a use has no valid path to Permitted or Discretionary under the current checkbox state, drop it from the "add a use" dropdown. But never remove a card the reviewer already added just because a checkbox changed later — re-evaluate and re-label that existing card instead of deleting their work.
  • Don't force a checkbox onto a condition the bylaw actually ties to a measured value (e.g. a public-area threshold in m²) rather than a yes/no fact. Leave that use's status static, spell out both thresholds in its summary text, and flag the caveat in the panel description instead of inventing a toggle for it.

08Force-refresh interaction rule

Every click that changes review data — a status pill, a use-selector pick, a "Remove from review," a filter chip — must trigger one shared refreshEverything() call that rebuilds the tab nav counts, the overall progress bar, and the whole main panel together, rather than patching only the element that was clicked.

// call this, not a targeted DOM patch, after any state-changing click
function refreshEverything(){
  const scrollTop = main.scrollTop;   // preserve position across the rebuild
  renderTabNav();
  renderOverallProgress();
  renderMain();
  // restore scrollTop via requestAnimationFrame, guarded for environments without it
}

Preserve scroll position across the rebuild so this doesn't feel jumpy on a long card list, and guard any requestAnimationFrame call with a typeof check so a stripped-down preview environment can never throw. Text inputs (notes, search, project fields) are the one exception — those update local state directly on input without forcing a full rebuild, so typing never loses focus.

10Build procedure, step by step

  1. Fill in the district worksheet from §02 — confirm current Part/Division numbers on calgary.ca for that district's category. Don't assume any category's numbering carries over to another; Residential, Commercial, Industrial, and Special Purpose are each numbered independently.
  2. Extract every applicable section for the general division, the district division, and the citywide rules, into plain-English summaries per §02's extraction rule.
  3. Extract the full permitted + discretionary use list for the district, one use-tab item per use, summary starting Permitted — or Discretionary — with its enabling section number and any use-specific caveat (GFA caps, adjacency conditions, etc.).
  4. Copy an existing checklist file (e.g. IG_Zoning_Review_Checklist.html) as the starting point — the CSS, the rendering engine, the session/export logic, and the use-selector logic are all built against the canonical general/district/citywide/use keys from §03, so they carry over unchanged to any category without rewriting.
  5. Replace CHECKLIST_DATA with the new district's content under those same four keys, and update the TABS array's labels/short codes (§01/§04) to show the new category's actual Part/Division numbers and district name.
  6. Update the Instructions tab copy — workflow order, district name, and the "what this does not cover" list, since scope carve-outs differ district to district and category to category (a residential district's exclusions look nothing like an industrial one's).
  7. Update panelDescription() for the new district's rule content.
  8. Check for a binary building-status flip (§07) — if the district's rules make any use's Permitted/Discretionary status, or its availability, depend on a yes/no fact about the building rather than the use, add the sidebar checkboxes and live-computed logic from §07 instead of hardcoding one status into CHECKLIST_DATA.
  9. Run the QA checklist in §11 before treating it as shippable.

11QA checklist before shipping

  • Both inline <script> blocks parse with zero syntax errors.
  • No calls to window.storage, localStorage, or sessionStorage anywhere in the file.
  • Every use-tab item's summary matches /^(Permitted|Discretionary)\b/i — confirm the count of matches equals the total item count for that tab.
  • Item counts per tab match your source extraction (spot-check the total against the bylaw's own use-list count).
  • Export → re-import round trip: fill every item (mix of all 4 statuses + N/A), include notes with embedded commas/quotes/newlines and project fields with commas/quotes, export, import into a fresh load, diff every field — zero mismatches.
  • Filename produced by export matches [Project Number] - [Date] - LUB Review.csv exactly, with unsafe characters stripped from the project number.
  • Clicking a status pill updates: the card, the stat strip, the tab count badge, and the overall progress bar — all in the same click, no stale numbers anywhere on screen.
  • Selecting a use from the use-tab dropdown immediately shows its card; removing it immediately hides the card and updates counts.
  • Before any use is selected, the use tab shows 0/0, not 0/(total uses in the district).
  • File opens correctly via file:// directly (double-click) — not just when served over http://.
  • If the district uses the §07 building-status checkboxes: toggling either one immediately re-labels every affected use card and re-filters the "add a use" dropdown, in the same click; a use already added to the review stays on screen (re-labeled, not removed) if a later toggle makes it invalid; both checkboxes round-trip correctly through export/import.
